# Ingress controllers and the resources they touch

A reference for what an **ingress controller** actually is, the full set of Kubernetes resources it interacts with, and how each piece maps back to the manifests in this folder.

This is concept-first reading; for the lab walk-through see [README.md](README.md).

## The shortest possible definition

The Kubernetes API ships an `Ingress` resource (`networking.k8s.io/v1`). It is **inert by itself** — a YAML file that describes "I want hostname X on path Y to land on Service Z, with TLS from Secret S." Nothing in the core Kubernetes control plane reads that resource and turns it into a real network listener.

An **ingress controller** is the missing piece: a separate piece of software running in the cluster that watches `Ingress` objects and reconciles them into a real reverse proxy (or programmes a cloud load balancer) that actually accepts HTTP(S) traffic from outside the cluster and forwards it to pods.

Concretely, in this lab:

- The **Ingress resources** live in [manifests/ingress-test-ingress-1.yaml](manifests/ingress-test-ingress-1.yaml) and [manifests/ingress-test-ingress-2.yaml](manifests/ingress-test-ingress-2.yaml).
- The **ingress controller** is `ingress-nginx`, installed by [setup-ingress-demo.sh](setup-ingress-demo.sh) step 1 from upstream `deploy.yaml`. It is just a Deployment + Service + RBAC + webhook.

If you delete the controller, the Ingress objects still exist but no traffic flows. If you delete the Ingress objects, the controller still exists but has nothing to route.

## The two resource maps

There are two distinct sets of objects involved. The first set is created **once, by the controller install**, and lives mostly in the `ingress-nginx` namespace. The second set is created **per-application**, by whoever wants something exposed, and lives in the application's own namespace.

### A. Resources the controller install creates

These all come from the upstream `deploy/static/provider/cloud/deploy.yaml` manifest. They exist regardless of whether any user has written an `Ingress` object yet.

| Resource | Name (in this lab) | What it does |
|---|---|---|
| `Namespace` | `ingress-nginx` | Isolation boundary for the controller and its supporting objects. |
| `IngressClass` | `nginx` | Cluster-scoped object whose `spec.controller` field is `k8s.io/ingress-nginx`. An `Ingress` opts into this controller by setting `spec.ingressClassName: nginx`. |
| `Deployment` | `ingress-nginx-controller` | The actual nginx process. Reads Ingress objects via the API server, rewrites its own `nginx.conf`, reloads. |
| `Service` (LoadBalancer) | `ingress-nginx-controller` | The single ingress point. MetalLB assigns it `192.168.48.201` (see step 2 of [setup-ingress-demo.sh](setup-ingress-demo.sh) — the `metallb.universe.tf/loadBalancerIPs` annotation pins it). All client traffic enters here. |
| `Service` (ClusterIP) | `ingress-nginx-controller-admission` | Backend Service for the validating webhook. Internal only. |
| `ConfigMap` | `ingress-nginx-controller` | Global controller tuning (proxy timeouts, log format, etc.). Empty by default; this lab doesn't customise it. |
| `ServiceAccount` + `ClusterRole` + `Role` + bindings | `ingress-nginx`, `ingress-nginx-admission` | The controller pod needs to **read** Ingress, Service, Endpoints/EndpointSlices, Secrets, Pods cluster-wide, and **patch** Ingress status (`.status.loadBalancer.ingress`) so `kubectl get ingress` shows the LB IP. |
| `ValidatingWebhookConfiguration` | `ingress-nginx-admission` | API-server webhook that rejects bad Ingress objects (e.g. malformed paths, conflicting annotations) before they're stored in etcd. |
| `Job` (admission) | `ingress-nginx-admission-create`, `…-patch` | One-shot Jobs that generate a self-signed cert for the admission webhook and patch its caBundle into the `ValidatingWebhookConfiguration`. |
| `Secret` (admission) | `ingress-nginx-admission` | Holds the cert generated by the admission Jobs. Distinct from any user TLS secret. |

Inspect them with:

```shell
kubectl get all,ingressclass,validatingwebhookconfiguration -n ingress-nginx
```

### B. Resources an application creates to be exposed

These are created **per workload**, in the workload's own namespace. The controller doesn't care which namespace they live in — it watches cluster-wide.

| Resource | Example (this lab) | Role in the request path |
|---|---|---|
| `Ingress` | `web` in `test-ingress-1`/`test-ingress-2` | Declarative routing table: `host + path → Service:port`. Also lists which hostname uses which TLS Secret. |
| `Service` (ClusterIP) | `web-a`, `web-b`, `web-c` | The **upstream** the controller dials. The controller talks to the Service's `ClusterIP:port` (or, in modern ingress-nginx, directly to its EndpointSlice — see below). |
| `Endpoints` / `EndpointSlice` | autogenerated by Kubernetes | The set of pod IPs backing each Service. Updated by the endpoints controller as pods come and go. ingress-nginx watches these so it can reload routes when a pod IP changes. |
| `Deployment` (or any pod owner) | `web-a/b/c` | The actual pods. Selected into the Service by labels. The controller never references the Deployment directly. |
| `Secret` (`kubernetes.io/tls`) | `example-tls` | Holds the cert + key. Referenced by `Ingress.spec.tls[*].secretName`. **Must live in the same namespace as the Ingress** — Kubernetes does not cross-namespace these. |
| `ConfigMap` (app-specific) | `nginx-template` | Not seen by the ingress controller at all — it's just data the backend pods mount. Mentioned only because this lab's pods read their nginx template from it. |

The split is intentional: app teams create category B in their own namespaces, the platform team owns category A.

## How an Ingress object actually becomes traffic

A request from your laptop to `https://test-ingress-1.example.com/a` traverses these layers:

```
+-----------+    1. DNS / /etc/hosts    +-------------------+
|  client   | -------------------------> |  192.168.48.201   |  (MetalLB-assigned VIP)
+-----------+                            +-------------------+
                                                  |
                                                  | 2. ARP resolves the VIP to one of the
                                                  |    nodes (MetalLB L2 mode); kube-proxy
                                                  |    /Cilium DNATs to the controller pod
                                                  v
                                         +--------------------+
                                         | ingress-nginx-     |
                                         | controller pod     |
                                         |                    |
                                         |  3. Terminates TLS |
                                         |     using the cert |
                                         |     from Secret    |
                                         |     example-tls    |
                                         |                    |
                                         |  4. Looks at Host  |
                                         |     header + path  |
                                         |     against rules  |
                                         |     compiled from  |
                                         |     the Ingress    |
                                         |     resources      |
                                         |                    |
                                         |  5. Proxies to     |
                                         |     web-a Service  |
                                         +--------------------+
                                                  |
                                                  | 6. Service IP → EndpointSlice → pod IP
                                                  v
                                         +--------------------+
                                         |  web-a pod         |
                                         |  (nginx:1.27)      |
                                         +--------------------+
```

The interesting steps:

1. **DNS / hosts file.** The request arrives at the LB IP. Kubernetes is **not involved** in resolving the hostname — that's whatever DNS or `/etc/hosts` entry the client uses.
2. **MetalLB.** In L2 mode, one speaker pod ARPs for the VIP. Once the packet reaches a node, kube-proxy or Cilium (here: Cilium with `kubeProxyReplacement=true`) DNATs it to the controller pod's IP.
3. **TLS termination.** The controller picks the right cert by **SNI** — the hostname the client sent in the TLS handshake. It loads `tls.crt`/`tls.key` from the Secret named in `Ingress.spec.tls[*].secretName`. If no SNI match, it falls back to the default cert (ingress-nginx ships a fake one).
4. **Routing.** Now decrypted, the controller sees the HTTP `Host:` header and request path. It compiles the Ingress resources into nginx server/location blocks and dispatches to the right `upstream` block.
5. **Upstream selection.** The upstream is a Service from `Ingress.rules[].http.paths[].backend.service`. Modern ingress-nginx reads the Service's **EndpointSlice directly** and load-balances at L7 across the pod IPs — kube-proxy is bypassed for ingress→pod traffic.
6. **Pod.** A normal Pod-to-Pod packet from the controller pod to the backend pod.

## TLS modes the controller supports

The Ingress API has one knob (`spec.tls`), but ingress-nginx layers two more on top via annotations.

| Mode | What client sees | What pod sees | Controller role | Annotation |
|---|---|---|---|---|
| **Edge termination** (this lab's `test-ingress-1`) | HTTPS | HTTP | Decrypts at the edge, talks plaintext to upstream | (default; just set `spec.tls`) |
| **Re-encrypt** (this lab's `test-ingress-2`) | HTTPS | HTTPS | Decrypts to inspect path, re-encrypts to upstream | `nginx.ingress.kubernetes.io/backend-protocol: "HTTPS"` |
| **SSL passthrough** | HTTPS | HTTPS (same TLS session) | Forwards encrypted bytes by SNI; never sees the path | `nginx.ingress.kubernetes.io/ssl-passthrough: "true"` |

**Passthrough is the odd one out.** Because the controller never decrypts, it can only route by `Host` (SNI) — path-based routing is impossible. That's why this demo uses re-encrypt instead of passthrough for `test-ingress-2`: the `/a /b /c` fan-out requires the controller to read the path.

Upstream cert verification (when re-encrypting) is **off by default** — the controller will dial HTTPS but won't validate the upstream cert. To enable it, set `proxy-ssl-verify: "on"` and `proxy-ssl-secret: <ns>/<secret>` (the secret must contain a `ca.crt`). See [README.md § Why don't we verify the upstream cert?](README.md#why-dont-we-verify-the-upstream-cert).

## Path matching

`pathType` is part of the core Ingress API and has three legal values:

| `pathType` | Match for `path: /a` | Notes |
|---|---|---|
| `Exact` | `/a` only | Anything else is a 404. |
| `Prefix` | `/a`, `/a/`, `/a/anything` | Used by both ingress files in this folder — friendly for poking around with curl. |
| `ImplementationSpecific` | controller-defined | ingress-nginx treats it as regex if the path contains regex metacharacters; otherwise prefix. Avoid unless you're sure. |

When two paths could both match (e.g. `/a` and `/a/b`), longest match wins.

## How an Ingress opts into a controller

Two mechanisms — modern and legacy.

**Modern** (used here): set `spec.ingressClassName: nginx`. Kubernetes looks up an `IngressClass` cluster-scoped object with that name; its `spec.controller` field tells it which controller should reconcile the Ingress. ingress-nginx ships an `IngressClass` named `nginx` whose controller is `k8s.io/ingress-nginx`.

**Legacy**: the annotation `kubernetes.io/ingress.class: "nginx"`. Still recognised by most controllers but deprecated. Don't mix the two on the same Ingress object.

A cluster can have **multiple ingress controllers** (e.g. one nginx for general traffic, one HAProxy for a specific team) — each watches only the Ingresses whose class matches its own. One IngressClass per controller; one Ingress targets exactly one IngressClass.

## Annotations: the configuration surface

The Ingress API itself is intentionally minimal — it covers hostnames, paths, TLS, and that's it. Everything else (timeouts, body size, auth, redirects, rate limits, custom headers, regex rewriting, mTLS, canary weights…) is configured via **controller-specific annotations** on the Ingress object.

This is why moving from one ingress controller to another is rarely a literal "rename `ingressClassName`" — every annotation belongs to the controller's own dialect:

- ingress-nginx: `nginx.ingress.kubernetes.io/...`
- HAProxy: `haproxy.org/...`
- Traefik: `traefik.ingress.kubernetes.io/...`

The two annotations actually used by this lab are:

| Annotation | Where | Effect |
|---|---|---|
| `nginx.ingress.kubernetes.io/backend-protocol: "HTTPS"` | [manifests/ingress-test-ingress-2.yaml](manifests/ingress-test-ingress-2.yaml) | Controller dials upstream over TLS instead of plaintext. |
| `metallb.universe.tf/loadBalancerIPs: 192.168.48.201` | controller Service, set by [setup-ingress-demo.sh](setup-ingress-demo.sh#L29-L30) | MetalLB assigns this specific IP rather than picking the next free one in the pool. |

The full ingress-nginx annotation reference is exposed inside the controller pod at `/etc/nginx/template/nginx.tmpl` and online in the controller's user guide.

## Useful debugging entry points

```shell
# Did the Ingress get picked up? Look for status.loadBalancer.ingress[].ip,
# which the controller writes back after it has accepted the rule.
kubectl get ingress -A

# What did the controller compile? This is the live nginx config.
kubectl exec -n ingress-nginx deploy/ingress-nginx-controller -- cat /etc/nginx/nginx.conf | less

# Which backends does it think are healthy? ingress-nginx exposes its model
# of the world on port 10246 (status) inside the pod.
kubectl exec -n ingress-nginx deploy/ingress-nginx-controller -- \
  curl -s 127.0.0.1:10246/configuration/backends | jq

# Controller logs — every reload, every webhook decision, every 4xx/5xx.
kubectl logs -n ingress-nginx deploy/ingress-nginx-controller -f

# Did MetalLB hand out the IP?
kubectl get svc -n ingress-nginx ingress-nginx-controller
```

## When Ingress isn't enough: Gateway API

The `networking.k8s.io/Ingress` API was frozen by the Kubernetes project years ago — all new feature work has moved to **Gateway API** (`gateway.networking.k8s.io`), which splits the single `Ingress` object into:

- `GatewayClass` — analogous to `IngressClass`.
- `Gateway` — the listener (port + protocol + cert), owned by the platform team.
- `HTTPRoute` / `TLSRoute` / `GRPCRoute` — owned by the app team, attached to a Gateway. Path matching, header matching, weighted routing, mirroring, redirects are all first-class.

Cilium (already running on this cluster, see [../k8s-setup-w-cilium/](../k8s-setup-w-cilium/)) implements Gateway API natively. `ingress-nginx` upstream was archived **2026-03-24** with `controller-v1.15.1` as the last release (see [README.md § About the archived controller](README.md#about-the-archived-controller)). For new work, prefer Gateway API on the existing Cilium install over a fresh ingress-nginx deployment.
